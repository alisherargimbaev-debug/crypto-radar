## 🔴 ПРИОРИТЕТ 1 — CPU 100% / рестарты (3.2)

### Симптомы
- 18+ рестартов за 2 дня (один в ~1.5 часа)
- `[SKIP] checkSignals завис > 4 мин — принудительный сброс`
- CPU периодически 100%

### Возможные причины
- `checkSignals` зависает на API call (Bybit, OKX, или Supabase)
- Memory leak в каком-то компоненте
- Infinite loop в одной из стратегий
- Webhook/event handler накапливает работу

### План работы
1. **Investigation (1 час):**
   - Прочитать `checkSignals` функцию полностью
   - Найти все `await` без timeout
   - Понять последовательность вызовов
   - Посмотреть `pm2 logs --err` за последние 24 часа
2. **Hypothesis testing:**
   - Добавить логирование с timestamps перед каждым `await`
   - Запустить бот, дождаться зависания
   - Посмотреть какой именно `await` повис
3. **Fix:**
   - Обернуть hang-prone await в `Promise.race([call, timeout])`
   - Или ускорить конкретный API call (caching, batching)

### Риск: ВЫСОКИЙ
- Большой refactor
- Может сломать существующую логику
- Требует **полного дня** работы

### Что нужно подготовить
- Бот должен быть стабильно online
- Backup перед началом
- План rollback

## 🔴 ПРИОРИТЕТ 2 — Расхождение backtest vs live

### Проблема
- **Backtest mode=off:** WR 88.6% на 537 сделках
- **Live после fixes:** WR ~25-30% на ~10 сделках
- **Расхождение огромное**, даже после починки записи

### Гипотезы (нужно проверить каждую)

#### Гипотеза A — Backtest имеет hidden bias
**Что может быть:**
- Look-ahead в каком-то месте (мы думали что починили в v1.3, но может ещё есть)
- Symbol survivorship bias (тестировали только выжившие монеты)
- Slippage слишком оптимистичный (0.05% vs реальный 0.1-0.3% на тонких альтах)
- Не учитываем funding rates (только perps)
- Не учитываем real-time delays (между сигналом и open)

**Как проверить:**
1. Code review `backtest_s1_filtered.js` ещё раз — особенно entry logic
2. Сравнить backtest заходы с **реальными** Bybit candles в тот же момент
3. Тест с **более консервативным** slippage (0.2-0.5%)
4. Добавить симуляцию **delay** (5-30 секунд между сигналом и entry)

#### Гипотеза B — Live среда другая
**Что может быть:**
- В live торгуем **больше** символов чем в backtest (включая stocks, мемы)
- Конкретно эти **non-tested** монеты ухудшают статистику
- Trailing SL в реальности срезает прибыль (Trailing C должен исправить)
- Pipeline filters всё ещё применяются где-то (через checkPortfolioRisk)

**Как проверить:**
1. Разделить live сделки на категории:
   - Backtest crypto (BTC, ETH, SOL, XRP, DOGE, BNB, AVAX, LINK + ARB, OP, APT, SUI, INJ, TIA, NEAR, AAVE)
   - Stocks (CRCL, ORCL, ARM, MU и т.д.)
   - Exotic crypto (GIGGLE, BSB, BEAT, ORDI и т.д.)
2. Посчитать WR по каждой категории отдельно
3. Если **backtest crypto** даёт ~80% в live → backtest правильный, нужен whitelist
4. Если **всё плохое** → backtest overfit

#### Гипотеза C — Smaller sample size
**Что может быть:**
- 10 сделок недостаточно для статистики
- Backtest 537 — намного больше
- Variance объясняет разницу

**Как проверить:**
1. Подождать 50+ сделок в live
2. Сравнить WR на 50 vs backtest

### План работы

**Шаг 1 — Сбор данных (нужны 30+ сделок):**
- Не делать новые изменения 3-5 дней
- Дать накопить статистику
- Каждый день мониторинг с записью

**Шаг 2 — Categorize trades:**
- Скрипт сравнения Bybit vs DB
- Разделение по категориям символов
- Реальный WR/PnL/RR по каждой

**Шаг 3 — Detailed code review backtest:**
- Прочитать `backtest_s1_filtered.js` строка-за-строкой
- Найти любые potential look-ahead или upward bias
- Сравнить с live execution path

**Шаг 4 — Реалистичный backtest:**
- Slippage 0.2% (вместо 0.05%)
- Delay simulation (10-30 sec between signal and entry)
- Funding rate impact для длинных позиций
- Прогнать на тех же 6 периодах
- Сравнить с прежним backtest

**Шаг 5 — Решение:**
- Если **реалистичный backtest** = live → backtest изначально был overfit
- Если **реалистичный backtest** даёт 70%+, live 30% → проблема в live среде
- Действие based on результат
